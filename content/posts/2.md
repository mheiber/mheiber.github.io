The Way of Code is a [fun artifact](https://www.thewayofcode.com/#PS) that effortlessly invites engagement. As part of trying to take it on board, these are some reflections, with no particular overall point.

## Simplicity vs. Ease

Rubin aphorisms about simplicity in coding I believe are much more about ease than simplicity. Ease isn't bad, but there are hard trade-offs here.

Simplicity is actually difficult to achieve, and is often antithetical to ease.

I like Rich Hickey's distinctionating here, even though I often disagree with his other writings: [Simple Made Easy](https://github.com/matthiasn/talk-transcripts/blob/master/Hickey_Rich/SimpleMadeEasy-mostly-text.md)

> An example of simple-vs-easy in practice is that the standard library Hickey designed often biases toward ease-for-designer over simplicity: ["Clojure's Error Messages are Accidental"](https://ericnormand.me/article/clojure-error-messages-accidental).

The default code I see spit out by vibe coding tools often has many nice properties, but I wouldn't call a React Server Components app with thousands of dependencies to do basic things "simple".

## Prompt Engineer vs. Vibe Coder

> Prompt engineers keep reaching for power,
> thus they never have enough.
> The Vibe Coder does nothing,
> yet leaves nothing undone.

I suspect Rubin doesn't know what prompt engineering is or much about how vibe coding works. Prompt engineering is a subskill of vibe coding; there aren't vibe coders who don't engineer prompts.

> Not a criticism, it's entirely on brand for Rubin's approach to art that he doesn't know perceived details.

Re hunger for power: My biggest challenge in trying to vibe code for free is that the better vibe coding tools eat tokens for breakfast and that the better models are more expensive.

> "I'm not using AI and I'm not prompting it" -- Rick Rubin, in response to a question in the a16z interview about how he uses AI

## Product and Code

Some of the claims in Rubin's book apply more to product and some apply mostly to code and sometimes these are in direct tension.

I found it helpful to try to distinguish these when reading the book, but also when listening to the fascinating interviews with Rubin about vibe coding.

Rubin writes: "Therefore The Vibe Coder builds without laboring." and later "Things arise and he accepts them". However, when I've seen great code by colleagues and asked them how they came up with it, it often was only through great struggle that they produced a few lines that achieved much and with clear intent.

So I really doubt that vibe coding generally produces code innovation, though it may produce product innovation. Code is hardly the point of vibe coding.

In Rubin's [a16z interview](https://www.youtube.com/watch?v=7s9C92Pkcc0), there's discussion of democritization unlocking new capabilities. The hosts seem to take this as applying to product, which it probably does.

> Beautiful code, arising from Source,
> will be louded for its function.
> Breakthrough apps, arising from Source,
> will advance the cybercosm. -- Rick Rubin, spelling included

However, more people generating the same kind of code faster could only affect product. **Graying up the divide between product and code** is a completely different idea, unexplored in the podcast episode but hinted at by Rubin. Software that changes its source (or some interpreted+sandboxed plugin code) in response to users is a different thing than faster spins on old ways of building.

The Way of Code nudges in this direction of new ways of thinking about code with its embedded visualizations that invite tinkering with prompts. These interactions involve bouncing out to Claude rather than staying in-app but are a start in this cool direction I haven't really seen before.

> I do suspect that vibe coding produces buggier products, serving as a kind of anti-[Alloy](https://alloytools.org/).

> Create order before confusion begins. -- Rick Rubin

## On Human Expression

> "Guiding by example. Performing without action. This is The Vibe Coder’s way."
